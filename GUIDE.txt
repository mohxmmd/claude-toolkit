1. WHAT THIS IS
================================================================================

Four plugins for Claude Code. Three do work, one installs the other three.

  CRAFT      Improves an interface that already exists, without redesigning it.
             Ask any AI to improve a screen and it regenerates the screen.
             Craft changes the smallest thing that fixes the problem, and tells
             you what it deliberately left alone.
             A SKILL. You invoke it by name.

  CHARTER    Turns a two-minute interview into a project's working agreement
             AND its enforced permission boundaries. A rule written in prose is
             a suggestion; Charter also writes the rule that enforces it.
             A SKILL. You invoke it by name.

  TARS       An output style. Answers first in a line or two, tells you when
             you are wrong, and separates "implemented" from "verified".
             NOT a skill. It changes every response until you switch it off.

  FORGE      A bundle. Installs the other three in one command and adds
             /forge:setup, /forge:doctor and /forge:uninstall. Nothing else.

None of the three depends on the others. Install one, or all of them.

Running cost, if you install everything: about 600 tokens added to every
session (Craft ~293, Charter ~298). TARS costs nothing extra; it replaces
the default style rather than adding to it.

2. BEFORE YOU START
================================================================================

REQUIRED

  Claude Code 2.x
      Version 2.1.197 or newer if you want TARS installed as a plugin.
      Older versions can still install TARS as a plain file (section 4).

  git
      To clone the repository. Charter's scripts also use git at runtime.

NEEDED BY SOME PARTS

  Node 20 or newer      Craft's measurement scripts.
  A POSIX shell         Charter's scripts. On Windows this is the bash that
                        comes with Git for Windows, which Claude Code already
                        relies on. WSL works too.
  python3 or node       Used by the installer and uninstaller to edit your
                        settings.json safely. Either one is enough. Without
                        both, they tell you which lines to add or remove by
                        hand instead of corrupting the file.
  jq                    Optional. Used when present, never required.

CHECK WHAT YOU HAVE

  claude --version
  git --version
  node --version
  python3 --version

3. INSTALL EVERYTHING AT ONCE
================================================================================

THE ONE COMMAND (macOS, Linux, WSL)

  git clone https://github.com/mohxmmd/claude-toolkit.git
  cd claude-toolkit
  ./setup.sh

WINDOWS POWERSHELL, the same thing

  git clone https://github.com/mohxmmd/claude-toolkit.git
  cd claude-toolkit
  .\setup.ps1

WHAT setup.sh ACTUALLY DOES

  1. Adds the marketplace       mohxmmd/claude-toolkit, named "claude-forge"
  2. Installs the bundle        forge@claude-forge, which pulls in charter,
                                craft and tars
  3. Turns on auto-update       so you receive fixes without repeating this

  It backs up your settings.json before touching it, and it never deletes
  anything.

  Auto-update writes two things into your Claude Code settings:

      extraKnownMarketplaces.claude-forge.autoUpdate = true
          Refresh this marketplace and its plugins at session start.

      env.FORCE_AUTOUPDATE_PLUGINS = "1"
          Lets plugins update even when Claude Code's own auto-updater is off,
          which is the default on native and VS Code installs. This affects
          PLUGINS ONLY. It never updates Claude Code itself.

  The honest trade: you will run new versions without reviewing them first.
  That is the point, and it is a real trade-off. Opt out with:

      ./setup.sh --no-auto-update          (PowerShell: -NoAutoUpdate)

setup.sh OPTIONS

  --no-auto-update      Install, but do not enable automatic updates
  --auto-update-only    Only turn on auto-update, install nothing
  --help                Show the options

  PowerShell names: -NoAutoUpdate, -AutoUpdateOnly, -Help

BY HAND, NO SCRIPT, NO AUTO-UPDATE

  claude plugin marketplace add mohxmmd/claude-toolkit
  claude plugin install forge@claude-forge

AFTER INSTALLING, RESTART CLAUDE CODE.

  Plugins load at session start. Nothing you just installed exists in the
  session you typed the command into. This trips up almost everyone once.


================================================================================
4. INSTALL ONE THING AT A TIME
================================================================================

You do not need the bundle. Each plugin installs on its own.

  claude plugin marketplace add mohxmmd/claude-toolkit      (once)

  claude plugin install craft@claude-forge        just Craft
  claude plugin install charter@claude-forge      just Charter
  claude plugin install tars@claude-forge         just TARS
  claude plugin install forge@claude-forge        all three, plus the bundle

Restart Claude Code afterwards.

TARS AS A PLAIN FILE, WITH NO MARKETPLACE AT ALL

  ./install.sh                    installs to ~/.claude/output-styles/
  ./install.sh --dir /path/to/project/.claude/output-styles     one project

  PowerShell:
  .\install.ps1
  .\install.ps1 -Dir C:\path\to\project\.claude\output-styles

  This copies one markdown file. An existing TARS.md is backed up first as
  TARS.md.backup-<timestamp>. Nothing is ever deleted.

  Installed this way the style is called  TARS
  Installed as a plugin  it is called     tars:TARS

  A committed project-level copy gives a whole team the same style.

RUNNING FROM A LOCAL CHECKOUT (for trying a change before committing it)

  claude --plugin-dir /path/to/claude-toolkit/skills/craft
  claude --plugin-dir /path/to/claude-toolkit/skills/charter

  The forge bundle is the exception: it declares dependencies, and Claude Code
  silently disables a plugin whose dependencies cannot resolve. Load the three
  components directly instead.

CHECK WHAT IS INSTALLED

  claude plugin list
  claude plugin marketplace list
  claude plugin details craft@claude-forge


================================================================================
5. TURNING TARS ON
================================================================================

Installing TARS does not switch it on. It is an output style, and you pick it:

  1. Run  /config
  2. Output style  ->  tars:TARS     (or TARS if you installed the file)
  3. Run  /clear

Step 3 matters. Output styles load at session start, so the session you are
sitting in looks unchanged until you clear it. That reads as a broken install
when it is not.

To switch back: /config -> Output style -> Default.

6. FIRST RUN IN A PROJECT
================================================================================

Order matters a little. Charter first, then Craft.

  cd /path/to/your/project
  claude

  /charter:init      Two to five questions, about a minute. Surveys the repo,
                     verifies its commands, shows you a diff, and writes the
                     working agreement and the permission boundaries only
                     after you accept. It also offers to switch TARS on and to
                     wire Craft, since it knows what you have installed.

  /craft:atlas       Reads the product and records what Craft needs to know:
                     the design system, the conventions, the components. Writes
                     .craft/config.md, which is then YOUR file to edit.

  /craft <what you want changed>
                     The actual work. Plain English, or /craft diagnose first.

Charter before Craft, because Charter's setup offers to do part of Craft's
wiring for you. Running it first means the other two need less.

NOT SURE WHERE YOU ARE?

  /forge:setup       Reads this repository and prints the one command to type
                     next. Writes nothing.

  /forge:doctor      Reads every AI context surface in the repo (CLAUDE.md,
                     .claude/rules/, .ai/rules/, .craft/, auto-memory) and
                     reports what is stale, duplicated or contradictory, and
                     which prose claims an enforcement it does not have.
                     Reports only. Repairs nothing.


================================================================================
7. EVERY COMMAND
================================================================================

CHARTER

  /charter:init                     Set up Charter here. Asks, shows a diff,
                                    writes only after you accept.
    /charter:init --quiet           Skip the explanatory commentary
    /charter:init --dry-run         Show the proposal, write nothing

  /charter:status                   What Charter has set up in this repo

  /charter:check                    Check the repo against its charter
    /charter:check --drift          What changed since setup
    /charter:check --audit          Full audit of the boundaries
    /charter:check --promote        Promote a convention to an enforced rule

CRAFT

  /craft <plain English>            Improve the thing you describe
  /craft diagnose <target>          Diagnose first, change nothing

  /craft:atlas                      Read the product, write .craft/
    /craft:atlas init               First run (the default when .craft/ is new)
    /craft:atlas refresh            Re-measure after the design system changed
    /craft:atlas doctor             Report drift, staleness, config problems

FORGE

  /forge:setup                      Where am I, what should I type next
  /forge:doctor                     What is stale or contradictory in my docs
  /forge:update                     Version check, and update if behind
    /forge:update --check           Report versions only
    /forge:update --weekly          Turn on the weekly background check
    /forge:update --no-weekly       Turn it off
  /forge:uninstall                  Remove all of it (section 10)

TARS

  No commands. It is a style, selected in /config.

A NOTE ON WHY THESE NEED TYPING

  /charter:init, /charter:status, /charter:check, /forge:setup, /forge:doctor,
  /forge:update and /forge:uninstall only run when a person types them. Claude
  cannot decide to fire them. They write files, ask questions, or delete
  things, and none of that should happen because a model inferred it might be
  wanted.

8. WHAT GETS WRITTEN, AND WHERE
================================================================================

ON YOUR MACHINE (once, at install)

  ~/.claude/settings.json
      extraKnownMarketplaces.claude-forge      the marketplace entry
      env.FORCE_AUTOUPDATE_PLUGINS = "1"       plugin auto-update
      enabledPlugins."<name>@claude-forge"     one per installed plugin

  ~/.claude/output-styles/TARS.md
      Only if you used ./install.sh. The plugin install does not put a file
      here.

  ~/.claude/forge/
      Only if you turned on the weekly check (section 9): the hook script, the
      stamp that dates the last check, and the log. Plus a SessionStart hook in
      settings.json pointing at it.

  If CLAUDE_CONFIG_DIR is set, all of the above lives there instead.

IN EACH PROJECT (only when you run the setup commands there)

  CLAUDE.md
      A fenced block between  <!-- charter:start v1 -->  and
      <!-- charter:end -->. Capped at 35 lines. Nothing outside the fence is
      ever touched.

  .claude/settings.json  or  .claude/settings.local.json
      Charter's permission rules (deny / ask). Which file depends on the
      answers you gave: committed settings for a team repo, local settings for
      a solo one.

  .claude/rules/*.md          Path-scoped rules, when Charter wrote any
  .claude/charter.json        Charter's state. Never loaded into a session.
  .craft/config.md            Craft's config. Yours to edit after it is seeded.
  .craft/atlas/*.md           What Craft measured. Disposable, regenerable.
  .craft/state.json           Craft's state
  .craft/cache/               Added to .gitignore for you
  .forge/manifest.tsv         The receipt (see section 10)

FOUR WORDS THAT MEAN DIFFERENT THINGS

  Charter uses these precisely, and so does this guide:

  sandbox      The operating system enforces it.
  boundary     A "permissions" rule. Claude Code enforces it before the model
               ever sees the request.
  guard        A PreToolUse hook.
  convention   A line in a file. Nothing enforces it. The model follows it
               because it read it.

  Prose in CLAUDE.md is a convention. Only a permissions rule is a boundary.


================================================================================
9. UPDATING
================================================================================

THE SHORT ANSWER

  Check what you have, and update if you are behind:

    /forge:update           inside Claude Code
    ./update.sh --check     see the versions, change nothing
    ./update.sh             update

  PowerShell:

    .\update.ps1 -Check
    .\update.ps1

  Restart Claude Code afterwards. Plugins load at session start, so a new
  version applies to your next session, not the one you typed the command in.

  What --check prints:

    Versions
      charter    0.2.0    up to date
      craft      0.2.0    -> 0.3.0
      forge      0.2.0    up to date
      tars       1.2.0    up to date

WANT IT TO HAPPEN BY ITSELF? USE THE BUILT-IN

  Claude Code already has plugin auto-update, and it runs at EVERY session
  start. That is more often than any schedule you would set up by hand, it
  needs no script, and it is one command:

    ./setup.sh --auto-update-only          (PowerShell: -AutoUpdateOnly)

  That is the recommended answer for "keep these updated automatically".
  setup.sh turns it on by default, so if you installed with setup.sh and did
  not pass --no-auto-update, it is already on and there is nothing to do.

  It writes two keys into your settings:

    extraKnownMarketplaces.claude-forge.autoUpdate = true
        Refresh this marketplace and its plugins at session start.

    env.FORCE_AUTOUPDATE_PLUGINS = "1"
        Lets plugins update even when Claude Code's own auto-updater is off,
        which is the default on native and VS Code installs. Plugins only. It
        never updates Claude Code itself.

  The honest cost: you run new versions without reviewing them first. For these
  tools that trade is usually worth it, because they change often and a stuck
  version means hitting bugs that are already fixed. Weigh it differently for a
  marketplace you do not control.

  Check it is working:

    claude plugin list
    grep -i autoupdate ~/.claude/debug/$(ls -t ~/.claude/debug | head -1)

THE WEEKLY CHECK, FOR PEOPLE WHO DO NOT WANT PER-SESSION UPDATES

  ./update.sh --weekly        turn it on
  ./update.sh --no-weekly     turn it off

  PowerShell: .\update.ps1 -Weekly  /  -NoWeekly

  Use this only if you deliberately keep auto-update off but would still rather
  not fall six versions behind without noticing. If auto-update is already on,
  the script tells you the weekly check is redundant and asks before installing
  a second mechanism that does the same job.

  What it installs:

    ~/.claude/forge/weekly-update.sh    a small script, nothing else calls it
    a SessionStart hook in settings.json, marked "async" so it never delays
    the start of a session

  How it behaves:

    Six days out of seven      exits in milliseconds, does nothing
    On the seventh             refreshes the marketplace, updates the four
                               plugins in the background, appends the result to
                               ~/.claude/forge/update.log
    While one check is running a lock stops a second from starting
    If a check fails           it does not retry every session; it waits for
                               the next week and the failure is in the log

  Because the work happens in the background, an update it fetches usually
  applies from the session after next. Read the log if you want to know what
  happened:

    tail ~/.claude/forge/update.log

  Both --no-weekly and /forge:uninstall remove the hook, the script and the
  stamp file, and leave any other SessionStart hook you have exactly as it was.

UPDATING BY HAND

  claude plugin marketplace update claude-forge
  claude plugin update forge@claude-forge

  Or one component at a time:

  claude plugin update craft@claude-forge

TURNING AUTO-UPDATE OFF WITHOUT UNINSTALLING ANYTHING

  Delete the "autoUpdate" line from extraKnownMarketplaces in your
  settings.json, or set it to false. That is the whole undo.

FOR MAINTAINERS: UPDATES DO NOTHING UNLESS YOU RELEASE PROPERLY

  The plugin cache is keyed by version. Pushing to main without bumping a
  version ships nothing at all: "claude plugin update" replies "already at the
  latest version" and every user keeps the old code.

  Bump the version in BOTH plugin.json and .claude-plugin/marketplace.json for
  every change users should receive, documentation fixes included. CI checks
  that the two agree. See docs/PUBLISHING.md.

10. UNINSTALLING
================================================================================

THE SHORT VERSION

  /forge:uninstall

  It prints everything it found, asks once, and removes it. From a shell,
  with no plugin required:

  ./uninstall.sh --plan      See the list. Changes nothing.
  ./uninstall.sh             Remove it.

  PowerShell:
  .\uninstall.ps1 -Plan
  .\uninstall.ps1

  Restart Claude Code afterwards. The plugins stay loaded until the session
  ends, so /craft still appearing in the list is not a failed uninstall.

WHAT IT REMOVES, ON THIS MACHINE

  The four plugins                forge, charter, craft, tars
  The marketplace                 claude-forge
  Auto-update settings            extraKnownMarketplaces.claude-forge
                                  env.FORCE_AUTOUPDATE_PLUGINS
  Plugin enablement               enabledPlugins entries ending @claude-forge
  The output style setting        outputStyle, only when it is set to TARS
  The style file                  ~/.claude/output-styles/TARS.md, if
                                  install.sh put it there
  The weekly check                ~/.claude/forge/ and its SessionStart hook,
                                  if you turned it on. Other hooks are left
                                  exactly as they were.

WHAT IT REMOVES, IN THE REPOSITORY YOU RUN IT FROM

  .craft/                         Craft's state
  .claude/charter.json            Charter's state
  .claude/rules/*.md              Only the rules files Charter wrote
  The CLAUDE.md fence             Only the block between the charter markers
  Permission rules                Only the ones Charter added
  .gitignore lines                Only the ones Charter and Craft added
  .forge/                         The receipt itself

WHAT IT NEVER REMOVES

  CLAUDE.md itself. The fence is cut out; your prose survives byte for byte.
  Any settings file. Keys come out of it; the file stays.
  Any rule you wrote yourself.
  Anything outside the repository you ran it from.

WHY IT CAN BE THAT PRECISE: THE RECEIPT

  Charter and Craft append one line to .forge/manifest.tsv for every artifact
  they create and every file they edit. That file is why the uninstaller can
  pull one permission rule out of an array without touching the rule sitting
  next to it.

  Tab-separated, five columns, component / kind / path / a / b:

  charter  path       .claude/charter.json
  charter  fence      CLAUDE.md  <!-- charter:start v1 --> <!-- charter:end -->
  charter  settings   .claude/settings.json  deny  Bash(git push --force*)
  charter  gitignore  .gitignore  .claude/charter.json
  craft    path       .craft

    path       Delete it, and its parent if that leaves the parent empty
    fence      Cut the lines from the start marker to the end marker
    settings   Pull that one rule out of permissions.<bucket>, or with the
               bucket "key", drop that top-level key
    gitignore  Remove that one exact line

  Commit it or ignore it, as you prefer. Committed, a teammate can uninstall
  cleanly from their own checkout.

IF THERE IS NO RECEIPT (projects set up before it existed)

  It still works. The fallback finds the fence by its markers, and .craft/,
  .claude/charter.json and a TARS outputStyle by their known paths.

  The one thing it will not do is guess at permission rules. Charter's rules
  and yours sit in the same array and look identical, so it lists them and
  leaves them alone for you to delete. Running /charter:init once first
  regenerates the receipt, if you would rather it be exact.

BACKUPS: NOTHING IS DELETED WITHOUT A COPY

  A settings file        <file>.backup-<timestamp>, beside the original
  Anything in the repo   .forge-backup-<timestamp>/, mirroring the paths

  To undo an uninstall: copy the backup tree back over the project and re-run
  ./setup.sh. Delete .forge-backup-* once you are happy.

REMOVING ONLY PART OF IT

  ./uninstall.sh --keep-project     Keep this repo's files, remove the plugins
  ./uninstall.sh --keep-plugins     Remove this repo's files, keep the plugins
  ./uninstall.sh --keep-style       Keep the TARS output style
  ./uninstall.sh --keep-settings    Leave the user settings.json alone
  ./uninstall.sh --yes              No confirmation prompt, for scripts
  ./uninstall.sh --plan             Print and stop

  PowerShell: -KeepProject, -KeepPlugins, -KeepStyle, -KeepSettings, -Yes,
  -Plan

OTHER REPOSITORIES ARE NEVER TOUCHED

  Run it from each one. To find them:

  grep -rl 'charter:start' ~/your/projects --include=CLAUDE.md

BY HAND, IF YOU PREFER

  claude plugin uninstall forge@claude-forge --prune -y
  claude plugin marketplace remove claude-forge

  That removes the plugins and the marketplace. It does not clean your
  settings, the style file, or anything in your repositories.

11. TROUBLESHOOTING
================================================================================

"I installed it and nothing happened."
  Restart Claude Code. Plugins load at session start.

"TARS is installed but every answer still looks the same."
  Selecting the style is a separate step, and it needs /clear afterwards.
  See section 5.

"/craft or /charter:init is not in the list."
  claude plugin list          Is it installed and enabled?
  Restart if you installed it in this session.

"Charter says a rule is enforced but Claude did it anyway."
  Run /forge:doctor. It finds prose claiming an enforcement that no permission
  rule backs. Prose is a convention, not a boundary. See section 8.

"Claude ignores an instruction in CLAUDE.md."
  Usually two surfaces disagreeing and nothing saying which wins.
  /forge:doctor reports duplicates, contradictions and dead references.

"The installer said it could not edit my settings."
  It needs python3 or node to edit JSON safely, and refuses to hand-roll it
  with sed because that corrupts real settings files. It prints the exact
  lines to add. Add them, or install either runtime and re-run.

"Windows: bad interpreter, or scripts fail immediately."
  A CRLF checkout of a .sh file. The repository forces LF via .gitattributes,
  so re-clone rather than fixing files one at a time. The plugins need the
  bash from Git for Windows at runtime; WSL works too.

"The uninstall printed 'failed' for a plugin."
  It prints the exact command to retry, and does not retry silently. Run it.

"I interrupted an uninstall halfway."
  Re-run it. It finds what is left and removes only that.

"Am I running the latest version?"
  ./update.sh --check, or /forge:update. It refreshes the marketplace first,
  so the comparison is against what is actually published.

"I turned on the weekly check and nothing has happened."
  By design: it does nothing for the first seven days. Check the stamp with
  ls -l ~/.claude/forge/last-update-check, and the log with
  tail ~/.claude/forge/update.log. A hook also needs a Claude Code restart
  before it runs at all.

"I want everything back after uninstalling."
  Copy .forge-backup-<timestamp>/ back over the project, restore any
  <file>.backup-<timestamp> settings files, and run ./setup.sh again.
